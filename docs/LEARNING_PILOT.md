# Real-data Red/Blue strategy-learning pilot

The `learn` command runs bounded strategy adaptation on local IU radiographs and
whole reports, including indication context. This is LLM-generated persistent prompt
memory, not model-weight fine-tuning or DSPy optimizer training. No RadGraph or
handbook-selector change is mixed into this experiment; the reporting reference
pack stays fixed.

```bash
RADARENA_TEXT_MODEL=google/gemma-3-27b-it \
RADARENA_VISION_MODEL=google/gemma-3-27b-it \
.venv/bin/radarena learn --output runs/learning-pilot-2026-11-04 \
  --max-cost .50 --max-calls 100
```

A new output directory records the code/configuration hashes. Repeating the exact
configuration explicitly resumes completed stage checkpoints rather than rerunning
them. Failed requests and stages are retained. Changing code/configuration requires
a new output directory. The run stops on provider, parsing or budget failures;
it does not silently fill missing outcomes or retry indefinitely.

## Protocol fixed before evaluation

- Training studies: 113 (laterality), 102 (presence/absence), 1187 (severity).
- Development studies: 2088 (laterality), 1411 (presence/absence), 2070 (severity).
- Deterministic selection by split and error family, excluding the previous
  indication pilot's development studies. Training and development studies are
  disjoint. These are development data; the final test split remains unused.
- Blue before/after: identical six frozen development reports (three seed attacks
  and three unchanged controls), identical images/indications/reference pack,
  at most two image checks, empty versus learned strategy memory.
- Each of three training rounds: Red generates a fresh attack from images and a
  source report; Blue verifies it and its unchanged control. Code grades synthetic
  edit localization. Each role then makes its own LLM reflection call, producing
  the next version of at most five concise reusable strategy rules.
- Red before/after: generates an attack on the same development laterality study;
  both attacks face Blue with its original empty memory. This keeps the opponent
  fixed when inspecting Red's change. One probe cannot establish improved Red
  attack rate; syntactic attacks are not certified clinically valid.
- No development feedback enters memory updates. Memories freeze before the
  post-training development calls. We report the final checkpoint, not whichever
  development score looks best.

## Separation and feedback

Predictors take fresh typed inputs; LM history is a log, not a shared conversation.
Models have no filesystem, shell or general memory-reading tool. Red gets only its
own rules, source, images, indication and attack-localization outcome. It never gets
Blue's strategy memory, image observations or reflection notes. Blue gets only its
own rules, candidate, images, indication and image observations. Training reflections
also get explicitly labelled edit-localization feedback after the attempt; this is
supervision, not inference-time access to an answer key. Blue never receives Red's
private rationale, learned rules, or original report through these calls.

The orchestrator and researcher logs can see everything. This is enforced by
whitelisting role input dictionaries, not by OS isolation of researcher files.
A role's next inference receives only its own checkpoint's `rules`, not the other
role's notes, feedback, explanation or file path. Tests cover these boundaries and
resume behavior. All model-generated rules remain fallible; reflection does not
prove that a new rule is better.

## Artifacts and interpretation

- `audit/trace.md`, `audit/calls.jsonl`, `audit/budget.json`: every audited call,
  inspectable output, usage, failure, and conservative spending ledger.
- `memories/{red,blue}/v{1,2,3}.json`: distinct role-private memory versions,
  explanations and previous-memory hashes. These are generated by actual LLM calls.
- `feedback/{red,blue}/round-N.json`: exactly the feedback supplied to each updater.
- `train/round-N/`: generated Red edits/rationale and Blue's attack/control outputs.
- `blue_eval/{before,after}/`: paired development outputs.
- `red_eval/{before,after}/`: generated attacks against the same baseline opponent.
- `summary.json`, `results.md`: before/after metrics, completeness and limitations.

Explanations are model outputs, not access to hidden model reasoning. Metrics score
synthetic edits relative to source reports; controls are not adjudicated error-free.
A generated attack passing syntax checks may violate the requested semantic family
or be ambiguous on the image. Clinical validity and larger paired evaluation remain
necessary before claiming that either agent has become a better radiology system.

## Completed run: November 4, 2026

The pilot completed three real training rounds, six paired Blue development cases
at each checkpoint, and one matched Red development probe at each checkpoint.
There were 95 audited calls (including cache lookups and two failed requests).
Two vision-provider timeouts were explicitly resumed; all completed stages and
failed requests remain in the record. The exact original source and dependency lock
were archived under `implementation/` with a verified matching implementation hash.

| Metric | Before learning | After three memory updates |
| --- | --- | --- |
| Blue localization F1 | 0.333 | 0.500 |
| Blue correctly localized edits | 1/3 | 1/3 |
| Blue extra/incorrect sentence flags | 2 | 0 |
| Blue control false alarms | 1/3 | 0/3 |
| Blue abstentions | 0/6 | 2/6 |
| Blue strict decision accuracy | 4/6 | 3/6 |
| Red syntactic edits escaping localization | 1/1 | 1/1 |

Blue's localization F1 improved by removing false flags, not by finding more
injected edits. Its report-level detection recall fell from 2/3 to 1/3, and strict
decision accuracy fell because uncertainty does not count as a correct decision.
There is a caution-versus-detection tradeoff, not a demonstrated overall improvement.
There is no measured improvement for Red on this single probe; both attacks escaped
localization, and neither was independently certified image-valid.

The actual learned rules expose useful failure modes. Blue v1 proposed comparing
against the control report, which is unavailable at inference; this rule disappeared
in v2. Other versions overgeneralized from individual examples. Red's v3 rules
focused on severity and largely displaced earlier laterality/presence strategies.
One proposed 'severity' strategy changes mild to none, crossing the boundary into
presence/absence. Reflections can therefore introduce invalid or overly broad
strategies. A per-error-family strategy library, a rule-validity/promotion gate,
independent attack adjudication and a larger development evaluation are needed before
promoting these memories as generally better. The final test set remains unused.

Known successful-call reported costs sum to $0.01175128 (may include cache cost
accounting). Total audit accounting is $0.03878488, including conservative reserves
of $0.0135168 for each of two failed requests with unknown actual billing. This is
below the $0.50 experiment cap; it is not an account-wide provider invoice.

## Reusing frozen memories

Standard `demo` accepts `--red-memory PATH` and `--blue-memory PATH`; `evaluate`
accepts `--blue-memory PATH` for the Blue-tools arm. Omit the flags for empty-memory
baselines. For this pilot the final paths are:

```text
runs/learning-pilot-2026-11-04/memories/red/v3.json
runs/learning-pilot-2026-11-04/memories/blue/v3.json
```

The loader verifies the role and content hash, bounds the rules, and passes only
that role's rules into its predictor. It refuses a Red checkpoint in the Blue slot
and vice versa. Explanations and training IDs are not forwarded. Checkpoints and
hashes are recorded in new demo/evaluation metadata. There are no online updates
during ordinary demo/evaluation runs. These experimental memories are opt-in;
default baselines stay empty-memory. After software changes, use a new run directory
or the archived original implementation when reproducing the completed pilot.

Run `.venv/bin/python scripts/build_learning_walkthrough.py` to regenerate the
human-readable `walkthrough.md` from actual saved stage outputs.
